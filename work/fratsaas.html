Case study — 2026

FratSaaS

Recruitment operations app — member roles, pledge tracking, and CSV exports for running a rush process end to end.

  • ▪Auth.js sessions with argon2-hashed passwords
  • ▪Drizzle-managed Postgres schema on Neon serverless
  • ▪QR codes + WebSocket realtime, Vitest-covered
  • Next.js 16
  • Drizzle + Neon
  • Auth.js
  • TypeScript

The problem

Running a rush is a logistics problem wearing a social hat: a roster of prospects and members, who holds which role, which events people showed up to, and a paper trail the next set of officers can actually inherit. It usually lives in a pile of spreadsheets that only one person understands. FratSaaS is that pile turned into one app — member roles, pledge tracking, and CSV exports for running the process end to end.

Architecture

A single Next.js 16 (App Router, React 19) application, with the data and auth layers chosen to keep member records trustworthy:

  • Auth.js for sessions, with passwords hashed via argon2 — accounts are real, not a shared password on a whiteboard.
  • Drizzle ORM over Neon serverless Postgres, with schema changes managed as migrations and seed data scripted — so the database is reproducible rather than hand-edited.
  • Zod validation at the input boundary, and QR codes plus a WebSocket channel for live event check-in.
  • Vitest covering the pieces that carry state.

Why it's built this way

The unglamorous parts are the point. Role-based access and hashed credentials matter because the data is about real people; migration-managed schema and CSV export matter because an officer term is one year and the tool has to survive the handoff. The recurring theme across this site — any data with real consequences deserves real handling — is exactly what a members database is.
