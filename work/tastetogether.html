TasteTogether

A dining agent for two: each person names artists, films and shows they love, and it finds the restaurant the less-excited person will still be happy with.

  • ▪Scores every place for each person separately — fair by min()
  • ▪Streaming agent trace, every reason traced to Qloo data
  • ▪Also an MCP server: find_table_for_two from any agent
  • Next.js
  • Vercel AI SDK
  • Qloo
  • MCP
GitHub ↗Live ↗

The problem

"Where do you want to eat?" — "I don't know, you pick." Review apps rank what is popular; chatbots guess. TasteTogether starts from cultural taste instead of cuisine: each person adds a few artists, films, shows or books they love, and the agent reads both through Qloo's taste graph.

Fair for both

Every candidate restaurant is scored for each person separately. Per person, Qloo affinities are z-scored within a shared pool and place popularity is regressed out, so raw popularity can't win on its own. The duo score leans on min(fitA, fitB) — the pick has to work for the less-excited person.

The agent

A match is an agent run that streams real events to the UI: taste overlap → scouting from three angles (A's taste, B's taste, a no-taste baseline) → cross-scoring every candidate for both people → negotiation → explanation. A tool-using LLM step turns a free-text vibe into real Qloo tags, and may only pick tags the tool returned. The "why you'll both love it" lines are written from a JSON of verified facts — never invented dishes, hours or prices.

The same agent is exposed as an MCP server (find_table_for_two), so Claude or any MCP client can call it.

What I learned

  • Probing the live API shaped the design: "Berkeley, CA" geocodes to South Carolina, so the app always sends a point and radius.
  • Raw affinity scores aren't comparable across people — normalising per person on a shared pool is what makes "fair" mean something.
  • An in-app "Would it work without Qloo?" panel is the most convincing demo of why the data matters.
