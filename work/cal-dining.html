Case study — 2026

Cal Dining

Watches the UC Berkeley dining-hall menus for the foods you actually want, then emails you the dining hall and meal period when they show up.

  • ▪Scrapes live menus, matches your keywords, sends HTML alerts
  • ▪One-command install (pipx) + browser setup dashboard
  • ▪Runs serverless on a GitHub Actions schedule — laptop off
  • Python
  • GitHub Actions
  • SMTP
GitHub ↗

The problem

The Cal Dining menus change every day across several halls and three meal periods. If you actually care whether the clam chowder is on today, you end up refreshing the dining site by hand. I wanted the inverse: tell it the foods I like once, and let it tell me where and when they show up.

How it works

A small Python pipeline, four steps:

  1. Scrape the current Cal Dining menu page.
  2. Extract items grouped by dining hall and meal period.
  3. Match them against your keyword list.
  4. Send an HTML email — only when there are hits.

Setup as a feature

The friction in a tool like this is never the scraping — it's getting a non-technical person to configure and schedule it. So the install is one command, and configuration is a local browser dashboard rather than a config file:

pipx install git+https://github.com/victory-c/cal-dining-scanner.git
cal-dining-setup

The dashboard collects your alert email, keywords, halls, meals, and a schedule, and lets you run a test scan against today's menu before you trust it. Settings persist under the OS-appropriate app-data directory, so they survive reinstalls.

Running serverless

The interesting choice is where the scan actually runs. Two modes:

  • Cloud (recommended) — the dashboard forks the repo into your account, pushes your settings as Actions secrets and variables, and enables a workflow. The scan runs on GitHub's schedule, so your laptop can be off.
  • Local — a launchd / systemd / Task Scheduler entry every 15 minutes, for when you'd rather keep everything on your own machine.

To avoid hand-editing UTC cron across daylight-saving changes, the workflow fires every 15 minutes and the script itself decides — in your configured timezone — whether a scheduled slot is actually due, sending at most once per slot.

What I learned

  • The scheduling story is the product. "Every 15 minutes, decide in local time" is a small amount of code that removes an entire class of DST bugs.
  • Config-as-a-dashboard beats config-as-a-file when the target user is a hungry undergrad, not an engineer.
  • Menus can lag reality, so the tool is careful to say it's for convenience, not allergy or medical decisions — the honest caveat belongs in the product.
